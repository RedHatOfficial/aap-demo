# ADR-042: AAP-Focused Monitoring Addon

**Status**: Proposed

**Date**: 2026-11-16

**Authors**: aap-demo maintainers

**Related issue**: [#90](https://github.com/RedHatOfficial/aap-demo/issues/90)

## Context

Issue #90 requests an optional Grafana/Prometheus addon for customer demonstrations. It
needs to show AAP platform health, job activity, resource usage, and execution-environment
behavior, while remaining easy to enable, inspect, and remove from a local MicroShift demo.

The request is larger than a single dashboard file. It introduces a metrics collection
stack, a discovery contract with AAP services, a credential and route lifecycle, optional
demo-data generation, and additional CPU, memory, storage, and image-pull cost. The default
`aap-demo deploy` path must not inherit that cost.

The repository has both the legacy Bash addon contract and the Python addon registry
introduced by [ADR-040](040-addon-framework-and-bash-fallback.md). This implementation uses
the Python registry and native addon interface only; it does not modify the legacy Bash
command or its shell addon list.
ADR-032 identifies #90 as architecture-first work requiring resource analysis and live
contract validation. The issue also explicitly asks for ServiceMonitors, which requires a
Prometheus Operator or an equivalent controller; plain Prometheus scrape configuration
cannot satisfy that requirement by itself.

The design must also respect the repository's AAP access rules: AAP automation data is
accessed through the Gateway API, and the existing `aap-admin-password` secret is the
supported local demo credential source. Credentials and generated cluster state must stay
out of Git. Live validation on the current AAP deployment shows that the AAP Metrics Service
route is a JSON API rather than Prometheus text exposition, and its metrics API does not
accept a Gateway token as a Prometheus scrape credential. A direct ServiceMonitor against
that route would therefore produce no useful AAP time series.

The validated Gateway-proxied controller API is reached through the in-cluster Kubernetes
Service over HTTP. Kubernetes Services do not add TLS automatically; the AAP application
would need to serve HTTPS on that Service for an HTTPS target to be valid. OpenShift Route
TLS termination protects the external Grafana route, but does not change the protocol of
the internal AAP Service. The implementation therefore keeps the internal HTTP target and
records scoped Gateway credentials as a future security improvement.

## Decision

Build an opt-in native Python `monitoring` addon under `src/aap_demo/addons/`. Treat
`monitoring` as the canonical name and accept `prometheus` as a compatibility alias in the
Python registry. The addon is AAP-dependent and is not enabled by default.

### Collection and visualization architecture

The long-term target architecture is a minimal Prometheus Operator deployment with a
standalone Grafana deployment. The first implementation uses the measured standalone
fallback because the current supported MicroShift cluster has no Prometheus Operator CRDs
and the AAP Metrics Service is not a Prometheus scrape endpoint:

- Deploy standalone Prometheus and Grafana resources from the Python addon, with bounded
  requests, retention, and storage.
- Deploy an addon-owned JSON-to-Prometheus adapter using the pinned
  `prometheus-community/json-exporter` image. It queries Gateway-proxied AAP controller API
  JSON with a password file mounted from an addon-owned Kubernetes Secret and exposes
  internal scrape metrics.
- Use a static Prometheus scrape job for the adapter in the first release. Do not create
  inert ServiceMonitor resources when no operator is installed.
- Keep the operator/ServiceMonitor path as a future compatibility-gated extension; enabling
  it requires a separate live resource decision.
- Do not install the full kube-prometheus-stack bundle, Alertmanager, node-exporter, or
  unrelated cluster-wide dashboards unless a later ADR expands the scope.
- Run Prometheus and Grafana in the addon-owned `aap-monitoring` namespace.
- Use version-pinned, reviewable images and manifests. Do not pull an unpinned `latest`
  image.
- Configure a Prometheus resource with an explicit low-resource profile, bounded local
  retention, and only the AAP-focused ServiceMonitors that live validation proves useful.
- Configure Grafana from a Kubernetes Secret/ConfigMap generated by the addon, with a
  Prometheus datasource and version-controlled dashboard JSON.

Live validation is a release gate for the exact AAP and MicroShift versions supported by
the repository. It must prove the service names, ports, paths, labels, and metric names
before they are encoded in ServiceMonitors or dashboards. A dashboard may include a panel
only when its query has been observed against the supported deployment; otherwise it must
show an intentional no-data state or remain out of the first release.

If the minimal operator profile exceeds the documented demo resource budget or cannot be
made reliable on the supported MicroShift profile, the implementation must fall back to a
standalone Prometheus configuration with explicit scrape jobs. That fallback is a scope
reduction: ServiceMonitor support is then documented as deferred, not represented as
implemented. The implementation plan must record the measured resource result and the
chosen path in its pull request.

### Addon lifecycle and state

- `aap-demo enable monitoring` creates or updates `aap-monitoring` and is idempotent.
- `aap-demo disable monitoring` removes addon-owned namespaced resources, ServiceMonitors,
  routes, and local state without modifying AAP resources outside the monitoring namespace.
- The addon must wait for Prometheus and Grafana readiness, but a timeout must report the
  namespace and useful `kubectl` diagnostics rather than silently succeeding.
- `aap-demo status monitoring` reports readiness, the Grafana route, the internal Prometheus
  service endpoint, and the local credential-file path. It must not print the password by
  default.
- `prometheus` normalizes to `monitoring` before addon lookup, config persistence, status,
  and disable operations, so the two names cannot create separate installations.

Grafana's admin password is generated once, stored in a Kubernetes Secret in
`aap-monitoring`, and copied to the Python state path returned by
`Paths.addon_dir("monitoring")` with mode `0600` for local access. Re-enabling preserves the
existing password when the Secret is still present. The password is never committed, placed
in a manifest file, or printed in normal command output.

### Demo data

Demo-data population is a separate, idempotent helper exposed as
`aap-demo monitoring populate` (or the equivalent addon-specific command selected during
implementation). It uses the AAP Gateway API and `aap-admin-password`, creates resources
with an `aap-demo-monitoring-` prefix, and records no credential in source control.

Population is not required for monitoring installation to succeed. It may be rerun without
duplicating its job templates or projects, and it must have a cleanup operation that removes
only resources carrying the addon-owned prefix. The helper must fail clearly when AAP is not
ready or the Gateway API contract differs from the validated version.

### Resource, security, and portability boundaries

- Monitoring remains opt-in and does not change the default cluster resource request.
- Namespace-scoped RBAC is preferred. No broad SCC grant is allowed without a separate
  security justification and test.
- Retention, storage size, CPU, and memory limits are explicit configuration with defaults
  suitable for a demo cluster; the plan must include a preflight or clear failure when the
  requested profile cannot fit.
- Grafana uses the repository's existing nip.io/ingress conventions and its host must be
  derived from the live cluster where possible. Prometheus remains cluster-internal by
  default; an external Prometheus route requires a separate security decision.
- All generated files remain under the Python addon's state directory; no passwords, tokens, or
  cluster exports are written to the repository.
- The first implementation targets the Python command only. Legacy Bash and Windows parity
  are follow-up work and must not be changed by this implementation.

## Consequences

### Positive

- Customer demos gain an AAP-specific observability story with repeatable dashboards.
- ServiceMonitors provide declarative, reviewable discovery when the supported AAP services
  expose a stable metrics contract.
- The addon is isolated, optional, idempotent, and removable under the existing addon model.
- Low-resource settings and live contract validation reduce the risk of shipping dashboards
  that silently show invented or unavailable metrics.
- Demo-data generation is separated from collection, so users can monitor an existing AAP
  installation without modifying its control-plane content.

### Negative

- Even a minimal operator-based stack adds images, pods, storage, and startup time to a
  resource-constrained local cluster.
- Metrics endpoints and labels can vary across AAP versions, so dashboards require live
  validation and may need version-specific guards.
- The adapter adds a second authentication and API-compatibility boundary that must be
  monitored. The first Python slice reuses the existing local AAP admin credential because
  that is the validated demo secret available in this repository; a scoped read-only
  Gateway credential is a follow-up security improvement.
- The operator path adds CRDs and reconciliation behavior that must be cleaned up carefully.
- Demo-data population uses AAP write operations and therefore needs strict ownership,
  idempotency, and cleanup tests.
- If the operator profile does not fit the supported demo budget, the first release must
  defer ServiceMonitors and explain the resulting issue scope reduction.

### Neutral

- Core AAP deployment, credentials, and the default addon set remain unchanged.
- Prometheus and Grafana credentials remain local demo credentials, not a production secret
  management solution.
- The monitoring namespace owns monitoring resources; AAP namespaces remain owned by the
  core deployment and are not deleted by addon cleanup.

## Alternatives Considered

### Full kube-prometheus-stack

Rejected for the first implementation. It provides ServiceMonitor support quickly, but it
also brings Alertmanager, node-exporter, broad dashboards, and a larger resource and
upgrade surface than an AAP-focused customer demo needs.

### Standalone Prometheus and Grafana only

Rejected as the target architecture because it cannot satisfy the issue's ServiceMonitor
acceptance criterion. It remains the documented fallback if the minimal operator profile
fails live resource or compatibility validation.

### Directly scrape the AAP Metrics Service JSON API

Rejected because the deployed service exposes JSON endpoints and requires an authentication
flow that Prometheus cannot use as a plain scrape target. The adapter makes the conversion
explicit, testable, and scoped to the Gateway API contract.

### Modify the core AAP deployment to embed monitoring

Rejected because it increases the default resource footprint, couples optional demo
observability to every deployment, and makes cleanup and versioning less independent.

### Generate dashboards from a remote Grafana or SaaS service

Rejected because local demos need a self-contained experience, customer environments may
not have network access, and external credential/tenant management would expand the scope.

### Populate arbitrary historical AAP data through direct controller APIs

Rejected because the repository requires Gateway API access for AAP automation data and the
controller is an internal implementation detail. Population must use the supported Gateway
contract.
