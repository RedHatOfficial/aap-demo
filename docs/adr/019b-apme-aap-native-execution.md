# ADR-019b: APME AAP-Native Execution

**Status:** Rejected
**Date:** 2026-07-21
**Author:** Chad Ferman
**Reason:** Overcomplex and adds multiple new support needs like

**Operational addendum (2026-10-21):** The original AAP-native proposal below remains
rejected and is retained as history. The current addon runs playbooks locally in its
venv. The [image-delivery addendum](#operational-addendum-quay-image-delivery-2026-10-21)
records CI publishing and optional prebuilt image consumption without changing that status.

## Context

ADR-019 established the `apme-eap` addon using official APME playbooks via a bash wrapper with an isolated Python virtual environment. While functional, this approach had drawbacks:

1. **Redundant execution environment**: Created a separate venv when AAP already has execution environments
2. **Missed demo opportunity**: Didn't showcase AAP running automation workloads
3. **Slower first run**: Venv setup takes 1-2 minutes
4. **System dependencies**: Required local Ansible installation
5. **No UI visibility**: Playbook runs were opaque to users

**Key insight:** Since `aap-demo` deploys AAP, we can use AAP's REST API to execute the playbooks *within AAP itself*, eliminating the venv entirely.

## Decision

Replace venv-based `ansible-playbook` execution with **AAP REST API orchestration**. The addon now:

1. Uses AAP's REST API to create/update resources (Project, Inventory, Job Template)
2. Configures Git-based Project pointing to the repository branch
3. Launches playbook execution as an AAP job via REST API
4. Auto-generates service account token and configures job template defaults

### Implementation

### Final Architecture: Git-Based Project with Auto-Configured Defaults

The implementation uses **Git SCM** for project source and **Ansible playbooks** for AAP resource management, avoiding file copy overhead and improving AAP-native integration.

**Ansible Playbooks:**

1. **`playbooks/setup_aap_resources.yml`** - Creates AAP resources via REST API
   - Queries Default organization
   - Creates Git-based Project pointing to current branch
   - Triggers project sync to pull playbook content
   - Creates Inventory (localhost with `ansible_connection: local`)
   - Generates service account token with cluster-admin permissions
   - Creates Job Template with pre-configured defaults:
     - `openshift_api_url: "https://kubernetes.default.svc:443"` (internal cluster address)
     - `openshift_token: <auto-generated>` (service account token)
     - `openshift_project_name: "apme"`
     - All helm chart versions and settings

2. **`playbooks/launch_apme_deployment.yml`** - Executes APME deployment
   - Launches job using pre-configured template defaults
   - Waits for completion with polling
   - Streams job output and error messages
   - Reports success/failure with AAP UI link

3. **`playbooks/deploy_apme_portal.yml`** - Main deployment playbook (runs in AAP)
   - Uses `kubernetes.core` modules with token authentication (no kubeconfig)
   - Deploys portal and APME gateway via Helm charts
   - Direct chart URLs instead of helm CLI repository management
   - Works in AAP execution environments without additional dependencies

**Modified:** `addons/apme-eap/deploy.sh`

- `setup_minimal_venv()` - Creates venv with `ansible-core` (not full Ansible suite)
- `ensure_aap_token()` - Auto-creates token via playbook if not exists
- `deploy()` - Orchestrates playbooks instead of bash functions
- Removed dependency on `lib/aap-api.sh` (bash+curl approach)

**Key Implementation Details:**

```yaml
# Service account token generation (cluster-admin permissions)
- name: Grant cluster-admin to kube-system default service account
  ansible.builtin.command:
    cmd: kubectl create clusterrolebinding apme-deployer-admin --clusterrole=cluster-admin --serviceaccount=kube-system:default

- name: Generate OpenShift service account token
  ansible.builtin.command:
    cmd: kubectl create token -n kube-system default --duration=87600h
```

**Git-based project** (auto-syncs from repository):

```yaml
- name: Create project (Git SCM type)
  ansible.builtin.uri:
    body:
      name: "aap-demo-apme"
      scm_type: "git"
      scm_url: "https://github.com/RedHatOfficial/aap-demo.git"
      scm_branch: "{{ current_branch }}"
      scm_update_on_launch: true
```

**Token authentication without kubeconfig** (critical for AAP execution):

```yaml
# kubernetes.core modules use api_key directly, not kubeconfig
- name: Check if namespace exists
  kubernetes.core.k8s_info:
    kind: Namespace
    name: "{{ openshift_project_name }}"
    api_key: "{{ openshift_token }}"  # No default(omit)!
    host: "{{ openshift_api_url }}"
    validate_certs: false
```

**Helm without helm CLI** (uses repository URLs directly):

```yaml
- name: Install portal Helm release
  kubernetes.core.helm:
    chart_ref: "{{ portal_helm_chart_repo_url }}{{ portal_helm_chart_name }}"
    # NOT: "{{ repo_name }}/{{ chart_name }}"
```

**Job execution flow:**

```
setup_aap_resources.yml (run once locally)
  ↓
1. Create Git-based Project
   - URL: https://github.com/RedHatOfficial/aap-demo.git
   - Branch: current branch (apme-playbook)
   - SCM update on launch: true
  ↓
2. Trigger project sync
   - Wait for successful sync
  ↓
3. Generate service account token
   - Grant cluster-admin to kube-system:default
   - Create long-lived token (10 years)
  ↓
4. Create Job Template with defaults
   - Playbook: addons/apme-eap/playbooks/deploy_apme_portal.yml
   - Pre-configured with token and cluster URL
   - ask_variables_on_launch: true (optional overrides)
  ↓

launch_apme_deployment.yml (from AAP or locally)
  ↓
1. Launch "Deploy APME" job
   - Uses template defaults (no vars needed)
   - POST to /api/controller/v2/job_templates/{id}/launch/
  ↓
2. Poll for completion
   - Check job status every 5 seconds
   - Stream errors on failure
  ↓
3. Display results
   - Success/failure status
   - AAP Web UI link for full job output
```

## Consequences

### Positive

- **Zero manual configuration**: Auto-generates token and configures all job template defaults
- **AAP-native**: Showcases AAP running real automation (great demo story)
- **Git-based**: Uses standard AAP project model (no file copy hacks)
- **Web UI visibility**: Users can watch playbook execution in AAP UI
- **No helm CLI needed**: Uses `kubernetes.core.helm` with direct chart URLs
- **Execution environment ready**: Works in AAP EE without additional dependencies
- **Internal cluster networking**: Uses `kubernetes.default.svc:443` for pod-to-API communication
- **Proper RBAC**: Service account with cluster-admin via ClusterRoleBinding

### Negative

- **Initial complexity**: Token generation and kubernetes.core configuration took iteration
- **RBAC requirements**: Needs cluster-admin permissions (acceptable for demo environment)
- **API surface**: Multiple AAP API endpoints (`/projects/`, `/inventories/`, `/job_templates/`)
- **Debugging**: Must check AAP UI for job logs when troubleshooting

### Neutral

- **Namespace fix**: Also fixed MicroShift compatibility by replacing `Project`/`ProjectRequest` with `Namespace` (separate change in same commit)
- **Same playbooks**: No changes to official APME playbooks themselves

## Alternatives Considered

### 1. Keep venv approach (ADR-019)

**Rejected:** Misses opportunity to showcase AAP's capabilities and creates redundant execution environment.

### 2. Use AWX CLI

**Rejected:** Adds another dependency (`awx` CLI) and doesn't provide more value than direct API calls.

### 3. Git-based Project

Instead of `kubectl cp`, use a git URL pointing to the repo.

**Rejected:**

- Requires git server or public GitHub (aap-demo is often airgapped)
- Adds complexity (SSH keys, credentials)
- `kubectl cp` is simpler for local development

### 4. MCP Server for AAP

Use the (hypothetical) AAP MCP server instead of direct API calls.

**Future consideration:** If AAP MCP server becomes available, this would be cleaner than direct API calls.

## Consequences

### Key Learnings

1. **kubernetes.core auth behavior**:
   - `api_key: "{{ var | default(omit) }}"` causes module to fall back to kubeconfig when var is undefined
   - Must use `api_key: "{{ var }}"` (no default) to force token-only auth
   - Environment variables (`K8S_AUTH_KUBECONFIG`) must be unset, not set to empty string

2. **Helm without CLI**:
   - `kubernetes.core.helm_repository` requires helm binary
   - Use direct URLs: `chart_ref: "{{ repo_url }}{{ chart_name }}"` instead
   - Works in AAP execution environments without helm CLI

3. **AAP variable passing**:
   - `extra_vars` must be JSON-serialized: `| to_json`
   - Job template defaults eliminate need for launcher to pass variables
   - `ask_variables_on_launch: true` allows optional overrides

4. **Service account tokens**:
   - `kubectl create token` generates time-limited tokens
   - Requires ClusterRoleBinding for cluster-wide permissions
   - Internal cluster address (`kubernetes.default.svc:443`) works from pod-to-pod

## Deployment Issues and Resolutions

During initial deployment on MicroShift (OpenShift Local), several interconnected issues were discovered and resolved:

### Issue 1: Registry Hostname Detection Failure

**Problem**: `oc registry login` failed with "The public hostname of the integrated registry could not be determined"

**Root Cause**: Playbook configured to use OpenShift integrated registry (`image-registry.openshift-image-registry.svc:5000`) which doesn't exist in MicroShift

**Resolution**:

- Deployed `aap-demo-registry` addon providing HTTP registry at `registry.aap-demo-registry.svc.cluster.local:5000`
- Configured job template with `oci_registry` pointing to custom registry
- Set `skip_plugin_push: true` to bypass skopeo TLS verification issues with HTTP-only registry

### Issue 2: Hairpin NAT / Pod-to-External-Route Connectivity

**Problem**: OAuth application check failed - pods couldn't reach AAP Gateway API via external route `https://aap-aap-operator.apps.127.0.0.1.nip.io`

**Root Cause**: Network routing prevents pods from accessing their own external routes (hairpin NAT limitation in MicroShift)

**Resolution**: Use internal service URL for pod-to-pod communication

```yaml
aap_host: "http://aap.aap-operator.svc.cluster.local"  # Internal service, not external route
```

**Key Distinction**:

- **External URLs** (browser access): `https://aap-aap-operator.apps.127.0.0.1.nip.io`
- **Internal URLs** (pod-to-pod): `http://aap.aap-operator.svc.cluster.local`

### Issue 3: Malformed Portal URL from API Derivation

**Problem**: Portal URL became `https://redhat-rhaap-portal-apme.https://kubernetes.default.svc` instead of proper nip.io URL

**Root Cause**: Cluster domain derivation logic tried to extract domain from `https://kubernetes.default.svc:443`, which doesn't match the expected `api.*.` pattern

**Resolution**: Explicitly extract cluster domain from existing routes

```yaml
- name: Get AAP route hostname
  ansible.builtin.command:
    cmd: kubectl get route -n aap-operator -o jsonpath='{.items[0].spec.host}'
  register: aap_route_result

- name: Extract cluster domain from route
  ansible.builtin.set_fact:
    cluster_domain: "{{ aap_route_result.stdout | regex_replace('^[^.]+\\.', '') }}"
```

### Issue 4: Missing Job Template Variables

**Problem**: Sequential "undefined variable" errors for `aap_organization`, `portal_helm_release_name`, and all Helm configuration variables

**Root Cause**: Job template `extra_vars` didn't include variables expected by APME playbooks (which have defaults in their own defaults.yml files but AAP doesn't load those)

**Resolution**: Build comprehensive `extra_vars` dictionary in setup playbook

```yaml
job_extra_vars:
  # OpenShift connection
  openshift_api_url: "https://kubernetes.default.svc:443"
  openshift_token: "{{ openshift_token }}"
  openshift_project_name: "apme"
  openshift_cluster_domain: "{{ cluster_domain }}"
  openshift_validate_certs: false

  # OCI registry
  skip_plugin_push: true
  oci_registry: "registry.aap-demo-registry.svc.cluster.local:5000/apme"

  # AAP connection (internal service URL)
  aap_host: "http://aap.aap-operator.svc.cluster.local"
  aap_username: "admin"
  aap_password: "{{ aap_admin_password }}"
  aap_organization: "Default"

  # Portal configuration
  portal_helm_release_name: "redhat-rhaap-portal"
  aap_apme_prerequisites_oauth_application_name: "APME Portal OAuth"

  # Helm chart configuration (portal)
  portal_helm_chart_repo: "openshift-helm-charts"
  portal_helm_chart_repo_url: "https://charts.openshift.io/"
  portal_helm_chart_name: "redhat-rhaap-portal"
  portal_helm_chart_version: "2.2.3"
  portal_helm_install_timeout: 1800

  # Helm chart configuration (APME gateway)
  apme_helm_chart_repo: "apme"
  apme_helm_chart_repo_url: "https://ansible.github.io/apme"
  apme_helm_chart_name: "apme"
  apme_helm_chart_version: "0.1.2"
  apme_helm_release_name: "apme"
```

### Issue 5: Missing Helm Binary in Execution Environment

**Problem**: `Failed to find required executable "helm" in paths`

**Root Cause**: APME execution environment image only included `oc` and `skopeo`, not `helm`

**Resolution**: Rebuilt execution environment with helm

```dockerfile
# execution-environment/Containerfile
RUN microdnf install -y openshift-clients skopeo tar && \
    microdnf clean all

# Install Helm manually (not in RHEL9 minimal repos)
RUN curl -fsSL https://get.helm.sh/helm-v3.14.0-linux-arm64.tar.gz | tar -xz && \
    mv linux-arm64/helm /usr/local/bin/helm && \
    chmod +x /usr/local/bin/helm && \
    rm -rf linux-arm64
```

### Issue 6: Incorrect Helm Module Parameter Usage

**Problem**: Helm failed with `404 Not Found` trying to fetch `https://charts.openshift.io/redhat-rhaap-portal`

**Root Cause**: Roles concatenated repo URL and chart name: `chart_ref: "{{ repo_url }}{{ chart_name }}"` instead of using separate parameters

**Resolution**: Use `chart_repo_url` parameter

```yaml
# Before (incorrect)
chart_ref: "{{ portal_helm_chart_repo_url }}{{ portal_helm_chart_name }}"

# After (correct)
chart_ref: "{{ portal_helm_chart_name }}"
chart_repo_url: "{{ portal_helm_chart_repo_url }}"
```

**Historical note (superseded):** ADR-019b is **rejected**; execution follows [ADR-019](019-apme-playbook-addon.md). Issues 7–9 below were written during AAP-native bring-up. **Current policy:** one `rhdh_image_tag` for all CPU paths (see **Supported RHDH hub version** in ADR-019); ARM differs by **registry/image**, not by tag.

### Issue 7: ARM64 Image Availability

**Problem**: `ImagePullBackOff` - Red Hat registry images don't have ARM64 builds

```
no image found in image index for architecture "arm64", variant "v8", OS "linux"
```

**Root Cause**: `registry.redhat.io/rhdh/rhdh-hub-rhel9` is x86_64 only (no arm64 manifest).

**Resolution**: Architecture-aware **registry/repository** selection; use the same `rhdh_image_tag` from aap-demo defaults on both CPU paths (substituted into Helm values—not separate ARM vs x86 tag pins).

```yaml
- name: Detect system architecture
  ansible.builtin.set_fact:
    system_arch: "{{ ansible_architecture }}"

- name: Use community RHDH images for ARM64
  ansible.builtin.set_fact:
    rhdh_image_registry: "quay.io"
    rhdh_image_repository: "rhdh-community/rhdh"
  when: system_arch in ['aarch64', 'arm64']

- name: Use official Red Hat registry for x86_64
  ansible.builtin.set_fact:
    rhdh_image_registry: "registry.redhat.io"
    rhdh_image_repository: "rhdh/rhdh-hub-rhel9"
  when: system_arch not in ['aarch64', 'arm64']

# Tag: {{ rhdh_image_tag | default('1.10') }} from addons/apme-eap/defaults.yml
```

### Issue 8: Postgres Registry Override

**Problem**: Postgres pod failed with `unauthorized: access to the requested resource is not authorized` on `quay.io/rhel9/postgresql-15`

**Root Cause**: Overly broad regex replacement changed postgres registry from `registry.redhat.io` to `quay.io`, but postgres image on quay.io requires authentication

**Resolution**: Make image replacement specific to RHDH hub only

```yaml
# Target only RHDH hub image, not postgres or other images
- regexp: '(pullSecrets: \[\]\n\s+registry: )registry\.redhat\.io(\n\s+repository: rhdh/rhdh-hub-rhel9)'
  replace: '\1{{ rhdh_image_registry }}\2'
```

### Issue 9: Plugin compatibility on ARM (community hub image)

**Problem**: Init container error — `backstage-community-plugin-scaffolder-backend-module-quay-dynamic` not found when using the community hub on ARM.

**Root Cause**: Values assume Red Hat packaged RHDH plugin bundles; the community hub image used on ARM may omit some artifacts—not an intentional split of RHDH **version tags** between CPUs (see ADR-019).

**Resolution**: Remove incompatible plugins for community hub path on ARM64

```yaml
- name: Remove incompatible plugins for community RHDH (ARM64)
  ansible.builtin.lineinfile:
    path: "{{ apme_portal_helm_values_path }}"
    regexp: ".*backstage-community-plugin-scaffolder-backend-module-quay.*"
    state: absent
  when: system_arch in ['aarch64', 'arm64']
```

## Operational Addendum: Quay Image Delivery (2026-10-21)

### Scope and Execution Boundary

The [APME image workflow](../../.github/workflows/apme-eap-image.yaml) builds a portal
image containing all six APME plugins and publishes only to `quay.io/aapdemo/apme-eap`.
Image production runs in GitHub Actions; deployment remains the local wrapper/playbook
flow. Choosing a prebuilt image removes the local plugin push/image build from that
deployment, without requiring AAP-native execution or changing this ADR's rejected status.

Manual dispatch accepts `source_repo`, `source_ref`, and `publish_latest`. Matching
addon/workflow pushes to `main` publish only with repository variable
`APME_QUAY_PUBLISH_ENABLED=true`; pull requests never publish. There is no schedule or
upstream repository trigger. Each build resolves current inputs once and shares them
between native AMD64 and ARM64 jobs.

### Provenance, Credentials, and Publication Policy

`source_repo` defaults to `ansible/ansible-rhdh-plugins`; `ansible/apme` is an explicit
alternative when it owns the complete pack. `source_ref=latest` selects the newest
completed successful Actions run on the upstream default branch; an exact full lowercase
40-character SHA selects the newest successful run for that commit. No branch-name or
short-SHA input is accepted, and unusable artifacts do not cause fallback to an older run.

Exactly one non-expired artifact must match `APME_PACK_FORMAT` (`oci` by default, or `npm`),
with `apme`/`plugin` in its name; Docker/build/image records are excluded. The workflow
exposes `pack_format`. OCI names have an `oci` token; npm names have an `npm` token or
a plain `.tar.gz` suffix without `oci`. Zero or ambiguous matches fail with candidate
names. The standalone resolver accepts `APME_ARTIFACT_NAME` to override automatic
name/format filtering. Downloads may be ZIP-wrapped packs or raw gzip packs from
`archive: false` uploads. The resolver checks the payload digest when present,
calculates the pack SHA256, and validates all six expected plugin
identities. Extraction checks the digest and plugin set again. Incomplete four-plugin
packs, checksum mismatches, malformed archives, and wrong identities fail before publishing.

Actions repository secrets are `APME_ARTIFACT_TOKEN` (upstream Actions read access),
`QUAY_USERNAME` / `QUAY_TOKEN` (target repository push/pull), and
`REGISTRY_REDHAT_USERNAME` / `REGISTRY_REDHAT_PASSWORD` when the AMD64 base requires
authentication. The workflow's own `GITHUB_TOKEN` has only `contents: read` and does not
replace those credentials. Registry logins use stdin and environment-backed credential
helpers. Credentials must stay outside the repository. Runner access to
`ubuntu-24.04-arm` is also an operational prerequisite.

The resolve job retains `plugin-pack.tar.gz` and shell-safe `artifact.env` as
`apme-resolved-pack` for one day. Provenance includes repository/SHA, upstream run ID,
artifact ID/name, pack filename/format, and pack SHA256; OCI labels and the publishing
summary carry corresponding metadata. Retain that evidence and the final manifest digest.

For `T=apme-<full-source-sha>-<first-12-hex-pack-digest>`, CI publishes `T-amd64` from
`registry.redhat.io/rhdh/rhdh-hub-rhel9:1.9` and `T-arm64` from
`quay.io/rhdh-community/rhdh:1.9`. Only after both builds succeed does it publish `T` as a
manifest containing exactly `linux/amd64` and `linux/arm64`, verifying its remote digest
and platform set. A failed job can leave an architecture tag; publishing is not atomic.

Architecture and manifest publication check remote tags immediately before pushing and
refuse existing tags or uncertain registry responses. Rebuilt bytes cannot overwrite an
existing release through these commands. Local single-architecture pushes always use an
architecture suffix. Retry failed jobs only for tags still absent; reuse a published
digest after a later failure, or use new source/pack inputs for a full republish.
Checks do not configure Quay tag protection or provide atomicity across independent
publishers. Deploy the recorded manifest digest. `latest` is a moving convenience alias.
The first live dispatch must use `publish_latest=false` with the gate closed. After live
validation, set `APME_QUAY_PUBLISH_ENABLED=true`: matching main pushes promote `latest`,
while manual runs promote only with `publish_latest=true`. A premature manual latest
request fails before resolution; a manifest verification failure blocks promotion. This
gate governs CI, not explicit aliases from the single-architecture local build wrapper.

### Deployment, Private Pulls, and Fallback

An empty `apme_preloaded_image_ref` remains the default. A fully qualified immutable tag
or `quay.io/aapdemo/apme-eap@sha256:...` opts into prebuilt delivery. Skopeo inspects and
pins the digest, and Podman verifies all six plugin identities in an isolated read-only
container before Helm renders local `./dynamic-plugins/dist/...` paths. The cluster selects
the architecture child from the manifest; the deployment host must support that image
architecture for local validation. Check mode cannot establish live validity. Turning off
`apme_preloaded_image_verify` skips only the Skopeo lookup, not the six-plugin check.

Public repositories can use an empty `apme_preloaded_image_pull_secret`. Private pulls
need separate cluster credentials: configure that optional Secret name and
`apme_preloaded_image_auth_file` with an absolute path to a containers auth file containing
inline credentials for the selected registry. The role uses the file locally, creates or
updates a namespaced `kubernetes.io/dockerconfigjson` Secret with only that registry, and
renders the name in image `pullSecrets`. An empty name creates no Secret; the cluster
must then pull anonymously or use separately managed credentials. Local login does not
configure cluster pulls, and publication does not make a private repository public.

Without a prebuilt reference, the addon resolves the bundled OCI pack, runs
`apme_oci_push` then `apme_image_build`, and publishes via Podman to the local registry.
Cached images must pass the six-plugin checker before reuse; invalid caches rebuild and
failed rebuilds stop deployment. Custom packs require an independently verified SHA256.
Fallback Helm fields use the node-supported external registry route, preserve its
repository namespace, and pin the cached or newly pushed registry digest with an empty
tag. This prevents `IfNotPresent` from retaining old bytes after a forced/repair rebuild.
The internal service endpoint is used only where required for plugin OCI delivery.
With `skip_plugin_push: true`, both push and build are skipped and runtime OCI delivery
assumes the archive is already published. The fallback does not fetch GitHub artifacts;
fresh upstream selection belongs to the CI/local publishing command. The Ansible
`apme_source_repo` / `apme_source_ref` defaults do not trigger an upstream fetch.

The [Task 6 execution record](../../addons/apme-eap/TEST_PLAN.md#task-6-execution-record--2026-10-21)
separates offline evidence from pending live checks. Resolver/extractor/build-wrapper
fixture tests and syntax checks do not prove a registry push or cluster rollout. Live
Quay publication, base-image and runner access, both architecture manifests, public/private
pulls, x86/ARM64 prebuilt deployment, local fallback/Podman-machine publication, and
`latest` promotion remain pending. The publishing credentials were unset in the validation
process; no live workflow or cluster deployment was run. Keep the gate closed until the
test plan's live acceptance checks are recorded. See the [README](../../addons/apme-eap/README.md)
